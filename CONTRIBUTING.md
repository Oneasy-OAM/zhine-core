# Contributing to Zhiné

Thank you for your interest in contributing to Zhiné.

Zhiné is an open-source project for building a **Personal Intelligence Companion / 个人智慧伙伴** on top of an **Open Cognitive Architecture / 开放认知架构**.

This project is currently in the concept, architecture, and specification stage. Contributions should focus on clarity, correctness, governance, and careful technical design before large-scale implementation.

---

## 1. What You Can Contribute

Useful contributions include:

- architecture proposals;
- documentation improvements;
- specification drafts;
- memory schema design;
- evolution log design;
- personal benchmark design;
- model routing proposals;
- safety and security analysis;
- fairness and accessibility review;
- multilingual documentation;
- local model integration research;
- prototype code with clear scope;
- examples using synthetic or explicitly licensed data.

---

## 2. Project Principles

Before contributing, please understand and follow these principles:

1. personal data is private by default;
2. users should own their personal cognitive assets;
3. remote models assist by permission, not by ownership;
4. growth must be evaluated and rollbackable;
5. self-training must be controlled;
6. open architecture should prevent lock-in;
7. AI should be a shared human capability, not a privilege of the few;
8. Zhiné must not claim to copy consciousness, personality, or digital souls.

---

## 3. Contribution Types

### Documentation

For documentation changes:

- keep language clear and concise;
- avoid hype and exaggerated claims;
- preserve the project terminology;
- keep brand terms consistent;
- explain trade-offs honestly.

### Specifications

For specification changes, include:

- problem statement;
- proposed schema or protocol;
- examples;
- compatibility notes;
- security considerations;
- privacy implications;
- migration or rollback considerations.

### Code

For code contributions:

- keep scope small;
- include tests where applicable;
- avoid hidden remote calls;
- do not include real personal data;
- document storage and network behavior;
- make privacy and permission assumptions explicit.

### AI Ethics and Fairness

Reports and proposals about fairness, accessibility, language coverage, bias, privacy, and user sovereignty are valid contributions.

---

## 4. Proposal Process

Significant changes should begin with a proposal.

Use this format:

```text
Title
Problem
Proposed Change
Rationale
Impact on User Sovereignty
Impact on Privacy and Security
Impact on Inclusive AI
Compatibility
Migration / Rollback Plan
Open Questions
```

Significant changes include:

- memory schema changes;
- evolution log changes;
- model routing behavior;
- training pipeline design;
- remote model integration;
- plugin permissions;
- governance changes;
- brand positioning changes.

---

## 5. Pull Request Guidelines

A good pull request should:

- have a clear title;
- describe what changed and why;
- stay focused;
- reference related issues or proposals;
- update documentation if behavior changes;
- avoid unrelated formatting churn;
- disclose security, privacy, fairness, or compatibility impact.

---

## 6. Data Rules

Do not submit:

- real personal memory;
- private documents;
- private conversation logs;
- personal training data;
- confidential screenshots;
- private API keys;
- data you do not have the right to publish.

Use synthetic data or explicitly licensed public examples.

---

## 7. Review Criteria

Maintainers may review contributions against:

- alignment with Zhiné principles;
- clarity and correctness;
- privacy and security impact;
- user sovereignty impact;
- fairness and accessibility impact;
- compatibility with existing specs;
- test coverage or validation evidence;
- maintainability.

---

## 8. Community Conduct

All contributors must follow the Code of Conduct.

Technical disagreement is welcome. Personal attacks, harassment, discrimination, or bad-faith behavior are not.

---

## 9. Status

Zhiné is early. The most valuable contributions at this stage are careful thinking, precise documentation, architecture review, and small reference implementations that validate the core thesis.
